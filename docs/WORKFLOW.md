# Prototype → Plan → Autopilot → Review

QuakeCurrent의 핵심 개발 규칙은 작은 수직 슬라이스를 네 단계로 반복하는 것입니다.
한 번에 완성형을 설계하기보다 가장 큰 불확실성을 실행 가능한 증거로 줄이고, 그
결과를 다음 사이클의 입력으로 사용합니다.

여기서 Autopilot은 검토 없는 자동 코딩이 아니라, 반복 작업을 명령·스케줄·CI로
재실행 가능하게 만든 상태를 뜻합니다.

## 단계별 책임

| 단계 | 반드시 답할 질문 | 최소 산출물 | 종료 조건 |
| --- | --- | --- | --- |
| Prototype | 가장 먼저 확인할 위험은 무엇인가? | 동작하는 얇은 slice, 명시적 비범위 | 핵심 가설을 직접 확인할 수 있음 |
| Plan | 어떤 계약과 실패 경로를 고정할 것인가? | 범위, 데이터·UI 계약, 위험, 검증 항목 | 구현 순서와 판단 기준이 명확함 |
| Autopilot | 무엇을 사람이 기억하지 않아도 되게 할 것인가? | 테스트, 생성기, worker, CI 또는 반복 명령 | 같은 입력에 같은 검증을 반복할 수 있음 |
| Review | 무엇이 실제로 통과했고 무엇이 틀렸는가? | 실행 결과, 발견 결함, 수정·보류 판단 | 증거 수준을 과장하지 않고 사이클을 닫음 |

## 사이클 시작 규칙

새 사이클은 다음 항목을 먼저 적습니다.

1. 해결할 한 문장의 문제
2. 이번 사이클에서 가장 불확실한 가설
3. 구현 범위와 하지 않을 일
4. 성공을 판단할 자동·수동 검증
5. 실패했을 때 되돌리거나 보류할 기준

범위가 [SSOT](./SSOT.md)를 바꾸면 구현보다 먼저 SSOT와
[결정 기록](./DECISIONS.md)을 갱신합니다.

## 단계 실행 규칙

### Prototype

- UI·API·데이터 중 위험이 가장 큰 경로를 끝까지 연결합니다.
- 샘플·fixture를 사용할 때 실제 데이터와 혼동되지 않게 표시합니다.
- 배포, 인증, 확장성처럼 이번 가설과 무관한 문제는 비범위에 남깁니다.
- 구현량이 아니라 가설을 확인할 수 있는지로 종료를 판단합니다.

### Plan

- URL, REST, WebSocket, DB 중 상태의 소유자를 하나로 정합니다.
- 정상 경로뿐 아니라 offline, 빈 결과, 중복, 재연결과 잘못된 입력을 포함합니다.
- 생성물과 원본을 구분하고 변경 전파 순서를 정합니다.
- 성능 최적화는 현재 측정값과 승격 조건을 함께 기록합니다.

### Autopilot

- 순수 로직은 결정론적 단위 테스트로 고정합니다.
- 언어 경계는 snapshot·생성·drift gate로 자동 검증합니다.
- 반복 작업은 worker, script 또는 CI로 옮깁니다.
- 자동화가 통과했다는 사실과 제품이 올바르다는 판단을 같은 것으로 취급하지
  않습니다.

### Review

- 로컬 테스트, 프로덕션 빌드, SSR과 실제 브라우저 흐름을 구분해 확인합니다.
- 데스크톱·모바일, 키보드 접근, 오류·로딩 상태를 직접 봅니다.
- 발견한 결함은 증상, 원인, 수정 또는 보류 이유로 기록합니다.
- 로컬, 공개 CI, 배포 환경의 증거 수준을 명확히 구분합니다.
- 결과는 `통과·실패·실행하지 않음·차단됨·범위 밖`으로 구분합니다.
- 결함은 `C{cycle}-R{number}` 형식으로 증상·원인·수정·회귀 검증을 남깁니다.

## Definition of Done

사이클은 다음 조건을 모두 만족할 때 닫습니다.

- 합의한 수직 슬라이스가 시작부터 끝까지 동작
- 관련 unit·contract·type·lint·build 검증 통과
- 사용자 흐름에 영향이 있으면 SSR 또는 브라우저 E2E 통과
- 계약·DB·workspace 변경 시 권위 소스와 파생물이 함께 갱신
- SSOT·아키텍처·결정·검증 문서 중 영향받은 문서 갱신
- Review에서 발견한 결함과 보류 항목 기록
- 배포하지 않았다면 운영 성능이나 트래픽 성과를 주장하지 않음

## 증거 단계

| 단계 | 의미 | 표현 예시 |
| --- | --- | --- |
| 코드 존재 | 구현이 저장소에 있음 | “구현함” |
| 로컬 검증 | 현재 환경에서 명령·수동 검토 통과 | “로컬 통과” |
| 공개 CI | 특정 커밋의 Actions 작업 통과 | “CI 통과”와 실행 링크 |
| 배포 검증 | 실제 배포 환경에서 확인 | 배포 URL, 환경, 시점 |
| 운영 증거 | 실제 traffic·metric으로 확인 | 기간, 표본, 측정 방법 |

상위 단계의 증거가 없으면 하위 단계 결과를 상위 단계처럼 표현하지 않습니다.

## 변경과 문서 연결

| 변경 종류 | 함께 볼 문서 |
| --- | --- |
| 기능 범위·비범위 | SSOT, 결정 기록, `/project` |
| 컴포넌트·데이터 흐름 | 아키텍처 |
| 중요한 기술 판단 | 결정 기록 |
| 테스트·CI 명령 | 검증 가이드 |
| 사이클의 역사적 결과 | `/build-log` |

커밋 메시지는 변경 의도가 드러나는 한글로 작성합니다. 문서만 바꾸더라도 실행 가능한
계약과 충돌하지 않는지 검토하고, 기능 변경과 관련 문서 변경은 가능하면 같은
커밋에 둡니다.
